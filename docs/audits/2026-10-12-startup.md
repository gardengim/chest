# Startup optimization — October 12, 2026

## Critical path and changes

Previously, the frontend loaded all primary pages and discovery code before
mounting, then waited for listeners, debug state, configuration, the entire icon
scan, activities, intent subscription and pending shortcut handling in sequence.

The critical path now overlaps configuration/debug requests with listener setup
and the activity snapshot. The library appears as soon as those safe initial
values are ready. Running-instance state and event subscriptions remain mandatory;
unknown activity state cannot expose a launchable library. Events received during
the snapshot take precedence over that older snapshot.

- Creation, instance and Settings modules load when selected. Cached promises
  avoid remounting pages when unrelated state changes. Existing parent-owned
  drafts and pending submission guards remain intact.
- News/Explore modules load after the library's first frame, during an idle slot.
- Icons, Minecraft manifests and automatic updater initialization also run after
  that frame, independently. Slow icons, manifests, news, updater metadata and
  shortcut retrieval no longer hold the library screen open.
- `afterFirstPaint` centralizes scheduling and cleanup, uses an idle callback with
  a one-second timeout, and falls back to a short timer where unsupported.
- Partial event-subscription failure now removes the already-installed listener.
- `chest:startup` and `chest:library-ready` performance marks expose the frontend
  initialization interval. This excludes process launch/WebView construction and
  JavaScript loading before component mount.

## Measurements

Production Vite preview, macOS Apple Silicon, local headless Chrome, 100 fixture
instances, seven fresh browser contexts per case. The before build restores the
three changed startup files from their pre-change snapshots. The added Korean
error label is also present in that rebuilt fixture (72 bytes); the bundle-size
baseline below uses the original pre-change asset.

| Measurement | Before | After |
| --- | ---: | ---: |
| Main startup JS, uncompressed | 224,272 bytes | 144,473 bytes |
| Library ready, immediate fixture responses, median | 107.1 ms | 95.3 ms |
| Library ready, 500 ms injected per selected startup IPC, median | 2,596.8 ms | 590.8 ms |
| Filter immediately after startup, immediate fixture, median | 25.5 ms | 44.7 ms |
| Filter immediately after startup, delayed fixture, median | 28.0 ms | 36.5 ms |

The main startup bundle shrank approximately 35.6%. The delayed workload improves
approximately 77.2% because independent requests overlap and optional operations
leave the critical path. It intentionally delays configuration, debug state,
icons, activity and shortcut retrieval; these are simulated costs, not observed
native disk timings. Immediate-response samples overlap and do not establish a
statistically significant speedup. Deferred discovery work can overlap the first
filter operation; all measured filter samples remain below 103 ms. No filter
speedup is claimed.

All dependency chunks still ship. This moves parsing and initialization to when
needed; it does not claim a comparable reduction in total JS or installer size.
Raw samples and exact asset sizes are in
[the measurement record](../measurements/2026-10-12-startup.json).

## Reproduce

Build with `npm run build`, then serve with
`node node_modules/vite/bin/vite.js preview --host 127.0.0.1 --port 1422 --strictPort`.
In a second terminal, run:

```sh
CHEST_BROWSER_EXECUTABLE='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
node scripts/measure-startup.mjs --url http://127.0.0.1:1422 --samples 7 --ipc-delay 500
```

Omit `--ipc-delay` for immediate fixture responses. Use `--output path.json` to
save raw samples. The script accepts only local preview URLs and uses disposable
browser contexts with mocked IPC; it never opens a real Chest profile.

## Verification and remaining measurements

The full browser suite passed (71 tests), covering navigation/drafts, shortcut
handoff, updater behavior, accessibility and 100/500/1,000-instance libraries.
Production chunks passed 14 navigation/feature/startup checks. After adding the
final concurrency/safe-readiness case, all three startup tests passed against both
production and development builds (72 distinct browser cases now exist). Svelte
checking reports zero errors/warnings; the production frontend build passes.
The offline native release build with `--features tauri/custom-protocol` also
passes, and its embedded asset keys include the current main and deferred pages.

Native cold/warm
process-to-interactive time, WebView construction, signed bundle startup,
Windows/Linux hardware and realistic custom artwork remain separate measurement
gates. No native launch-time, CPU, RSS or battery percentage is inferred from the
browser benchmark.

## Packaged macOS follow-up

Rebuilt `Chest.app` with the Tauri bundler from current source, applied a local
ad-hoc signature, and passed strict/deep signature verification. Ran the packaged
executable with real WebKit, native IPC and public metadata endpoints. Used
isolated profiles with no accounts, no installed games, default icons and no
custom screenshots, on macOS 27.0.1 / arm64.

| Workload | Process creation to library render acknowledgement |
| --- | ---: |
| First launch in a fresh empty test profile | 1,016 ms |
| Empty-profile relaunches | 381 / 382 ms |
| 100-instance library, three samples | 464 / 406 / 410 ms |

The 100-instance median is 410 ms. The fresh launch includes new profile/WebKit
initialization and warm OS caches; it is not a cold-boot benchmark. The populated
profile was initialized before its synthetic config was written. Native trace
stages include profile isolation and the macOS-version subprocess check; they do
not isolate `Core` construction alone. These are current-build measurements,
without a matching pre-optimization native baseline.

The end boundary is native receipt of an IPC acknowledgement after two animation
frames following the usable-library commit. This is a render-readiness proxy,
not proof of when the compositor presents pixels or a Finder/Dock click-to-window
time. The local ad-hoc signature is not distribution signing/notarization.
Raw stage timings are in [the native measurement record](../measurements/2026-10-12-native-startup.json).

Native accessibility inspection confirmed the `tauri://localhost` test-profile
window with Library 100. Native input verified search narrowing to World 0099,
opening that instance, selecting Content, returning home, and restoring the full
library. The app was left open in its disposable profile. This is a basic native
interaction pass, not a full native accessibility or gameplay acceptance pass.
